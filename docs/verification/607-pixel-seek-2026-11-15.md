## Seek and timing findings

AirPin STD 5.7.1 advertises `Seek` and `REL_TIME`, matching Naviamp's command. Two-minute generated
16-bit/44.1 kHz stereo FLAC and an explicitly encoded original MP3 control were tested. The MP3
case is a separate diagnostic source, never a fallback for a FLAC request.

| Source | Encoded bytes | HTTP requests | Media loads | Play commands | Paused seek target/observed | After resume | Playing seek target/observed |
| --- | ---: | ---: | ---: | ---: | --- | --- | --- |
| Original FLAC | 1,871,384 | 4 | 1 | 2 | 30 s / 30 s | 0 s | 60 s / 0 s |
| Original MP3 control | 2,881,453 | 2 | 1 | 2 | 30 s / 30 s | 0 s | 60 s / 0 s |

Both seeks received successful action responses; pause/resume/stop states were independently
queried. One media load proves that Naviamp did not reset the stream with another SetAVTransportURI
during seek/resume. Sanitized raw playing-position response fields were:

```text
TrackDuration=00:00:00, RelTime=00:00:00, AbsTime=00:00:00
```

Thus the zero position is present in the receiver's response, rather than introduced by the time
parser. A temporary whole-second wire-format experiment did not establish an improvement (resume
timed out); production serialization was left unchanged. Actual audible seek position is still
unverified. Neither an acknowledgment nor a briefly echoed target proves where decoding resumed.

The investigation also exposed a Naviamp defect: zero receiver duration replaced a known finite
provider duration. External phone controls then rejected positive seeks as beyond the zero-length
track. The common regression first failed with **expected 180000, actual 0**. Core now treats
nonpositive receiver duration as unknown, preserving the known queue-track length. The regression
checks that external seek reaches the wire at 30 seconds without another media load, while
observed position remains zero; the fix does not synthesize successful progress.

## Pixel network isolation

Device: Pixel 6a, existing saved provider/data preserved while installing the PR debug app.
The opt-in instrumented acceptance uses MainActivity's actual process-owned Core, selects a finite
track from the saved provider through shared commands, selects AirPin through the shared picker,
and verifies that the media URL belongs to a local Pixel interface. It checks remote states and
records receiver and app positions. It does not use the desktop fixture as sender.

The first run failed on the main-thread send. After the dispatch fix, the exception disappeared,
but the Pixel still received no discovery responses with its existing Tailscale VPN active:

- AirPin description GET through the normal app HTTP engine: **HTTP 200**.
- Source-address-bound UDP multicast M-SEARCH: **no reply within four seconds**.
- Source-address-bound UDP unicast M-SEARCH to AirPin: **no reply within four seconds**.
- Explicit Android Wi-Fi `Network.bindSocket`: **EPERM / Operation not permitted**.

Tailscale is configured as the always-on VPN; Android's lockdown flag is off. This establishes
that direct Wi-Fi socket binding is disallowed in this configuration, but does not by itself prove
the cause of every missed multicast response. A comparison with the VPN paused is required.
No VPN settings were changed without authorization. Until that comparison and the actual handoff
pass, **Pixel sender acceptance remains unverified**, not passed.

The multicast lock was released after the timed-out scan (native Wi-Fi history recorded its
45-second lifetime). That cleanup observation is not a passing discovery result.

## Reproduction and native boundary accounting

Ordinary CI skips both operator-only Android probes. Install the debug app and instrumentation APK
without clearing data, and run the AndroidJUnitRunner with:

```text
-e class app.naviamp.android.AndroidAirPinLiveInstrumentedTest
-e liveAirPin true
-e airPinLocation <current description URL>
-e airPinUdn <current receiver UDN>
```

Optional `airPinName` defaults to `APTV_223`; `airPinSearch` defaults to `a`. The selected source must
contain a finite track longer than 90 seconds. The route-only diagnostic is selected with method
`#nativeWifiRouteDiagnostic` and `liveAirPinRoutes=true`; it is a network measurement, not casting
acceptance. Do not run these against a receiver in use by someone else.

The JVM probe additionally accepts `NAVIAMP_AIRPIN_DURATION=120` and
`NAVIAMP_AIRPIN_FORMAT=flac` (default) or `mp3`; the existing `NAVIAMP_AIRPIN_FLAC` file-path variable
points to the corresponding encoded fixture. Use `--rerun` for environment-only changes.

Changed platform production files in this follow-up:

- `apps/android/.../AndroidNaviampCoreCatalog.kt`: supplies the I/O dispatcher required by Android's
  prohibition on main-thread socket sends; all operation ordering and failure policy are common.
- `apps/desktop/.../DesktopComposition.kt`: supplies the JVM I/O dispatcher for blocking native UDP
  operations; it does not schedule discovery or interpret protocol results.

The instrumented test is platform-specific because it exercises Android Activity lifetime,
WifiManager locks, ConnectivityManager networks and the real installed native host graph.
Common tests and Android APK/test builds plus Desktop compilation and architecture checks pass.
The latest local full shared run passed **332 app + 642 presentation tests (974)**; the operator-only
JVM probe is skipped there and executed separately against AirPin. New source still requires its
own fresh full CI result. Android minimum remains API 26.

PR 608 remains draft. iOS native wiring, native lifecycle/GENA/notification work and real WiiM
lossless/gapless acceptance remain open; AirPin still omits `SetNextAVTransportURI`.
