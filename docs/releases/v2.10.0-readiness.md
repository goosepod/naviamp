## Apple operator handoff

The Xcode app's Debug and Release defaults now match 2.10.0 (60), guarded against
canonical VERSION/VERSION_CODE drift (#447). The app bundles a required-reason
manifest for its own UserDefaults settings/locale use (`CA92.1`). The unsigned-IPA
builder checks the **archived** manifest. This narrow declaration does not establish
that every embedded SDK's required-reason/signature obligations are complete.

On the signing Mac, use accepted source and the existing developer team:

```sh
xcodebuild -project apps/ios/Naviamp.xcodeproj -scheme Naviamp \
  -configuration Release -destination 'generic/platform=iOS' \
  -archivePath build/store-v2.10.0/Naviamp.xcarchive \
  DEVELOPMENT_TEAM="$NAVIAMP_APPLE_TEAM_ID" \
  MARKETING_VERSION=2.10.0 CURRENT_PROJECT_VERSION=60 archive
```

Inspect the archive's bundle ID, version/build, entitlements, native SDK privacy
manifests and signing. Use Organizer **Validate App** and App Store Connect export
with automatic version/build management disabled. Verify app privacy and encryption
compliance against the actual archive; do not copy Mac JVM crypto answers to iOS.
Keep the existing reviewer contact and dedicated demo-server access private. Retest
that the reviewer can connect and play without owning a personal server. Address the
existing iOS rejection, account warnings, age ratings, screenshots and support/privacy
URLs before submission. Use [the prepared copy](v2.10.0-store-copy.md).

For Mac store wrapping, use the packaging-only script and instructions at immutable
PR #249 source `548f6f2779bc36a345496480fb6d7092657cd6fd`, with a fresh final Mac
release bundle and **`--version 2.10.0 --build 60`**. It needs the existing app and
runtime provisioning profiles, Apple Distribution identity, installer identity and
JBRSDK 21. Preserve sandboxing, nested native signatures and quarantine cleanup;
verify the final PKG/archive. Existing draft validation does not establish acceptance
for this candidate. Missing current-source visible Mac/sandbox tests remain explicit
owner-accepted release deferrals, not completed store acceptance.

## Windows Store operator handoff

PR #324 is pinned to the original v2.9.0 ZIP. **Do not dispatch it unchanged.** For
v2.10.0, use its audited wrapping tool on a private staging copy with the final ZIP's
exact SHA-256 and accepted source commit, version code 60 and the existing identity.
MSIX identity version `2.10.60.0` is the packaging version (major/minor/build/reserved
zero), not a new public release or tag. Public app version stays v2.10.0.

Run MakeAppx with schema/semantic validation enabled, then the wrapper's independent
payload verifier. Retain manifest, hash, packaging log and provenance. Do not use
unsigned EXE/MSI as the Store submission: this channel uses MSIX, which the Store
signs after certification. Local MSIX sideload testing requires a temporary trusted
test signature and is separate from the standalone walkthrough. Verify fresh-data
credentials/relaunch, upgrade/coexistence and profile preservation in that package
before submission. Preserve the existing pending submission until its live status
and replacement action have been reviewed.

## Final release controls

- Refresh all-platform packages on accepted source and record successful verification
  and exact source provenance. A branch dispatch with blank `release_tag` prepares
  artifacts and **skips publication**.
- Reconcile the mistaken unpublished tag refs only when actually cutting the release.
  Original tag objects/annotations are preserved in the #440 audit. Neither tag has
  unique product work outside accepted main. No higher public version is introduced
  to work around them. Future v2.10.1 must follow the published v2.10.0.
- Create the draft from the accepted v2.10.0 tag, inspect every artifact and the release
  body, and verify the exact title **Naviamp v2.10.0** before and after publication.
- Publishing requires an **Announcements** GitHub Discussion with release highlights,
  fixes and upgrade/compatibility notes. A branch build receives no announcement.
- Store uploads/review/rollout remain separate operations. Do not replace a pending
  submission, accept account/legal declarations, invite testers or publish a store
  release merely because package preparation succeeded. Forgejo remains a manual mirror.
