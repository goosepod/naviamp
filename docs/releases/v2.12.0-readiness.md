# v2.12.0 release readiness

Issue: https://github.com/goosepod/naviamp/issues/635
Milestone: https://github.com/goosepod/naviamp/milestone/12

## Frozen scope

Base: public v2.11.3. `release/2.12.0` was cut from accepted `main` commit
`f16264a2f` (Save the iOS compiler cache again by skipping booted-simulator tests, #634).

Selected scope: Apple TV beta (#590), CarPlay beta (#43), Android Auto UX and capability
cleanup (#350), Aurral as an optional companion to a primary music server (#587), and internal
build/CI work (#592, #633).

Release metadata on `chore/635-release-preparation`: VERSION `v2.12.0`, VERSION_CODE `65`
(v2.11.3 shipped as 64). The release branch still lacks the v2.11.3 changelog section and
hotfix metadata (#600 is open); both must be carried into this preparation PR.

## Release blockers

1. **Aurral 3 support (#587) — merged in #636, ported in #648.** Aurral
   3.0.1 reports app API version 2 and dropped the v1 feature names, so the v1-only client
   disabled every Aurral surface. Owner decision (2026-11-20): support Aurral 3.x only and
   drop Aurral 2.x. The shared client now requires API version 2 and maps the v2 contract
   (Library IDs from `libraryAlbumId`/`album.id` with boolean `managed`, `/api/library`,
   `/api/library/albums/:id/status`, `accessPlaylists`, v2 monitoring bodies, no
   `triggerSearch`, no Lidarr manager). Aurral 3's session-only release cover route is read
   through the cover list so the session never follows its external redirect. Verified:
   provider Aurral unit suites (all pass), `AurralLiveTest` 15/15 against the owner's live
   3.0.1 server, and on the Pixel 6a: companion Home card, recommendations (500),
   artist details, sample playback, release covers, recent requests and Trending. Request,
   monitoring and feedback writes were not exercised against the live server. Upgrade note
   for release text: Aurral 2.x servers are no longer supported. README updated.
2. **In-app changelog — updated on `chore/635-release-preparation`.** CHANGELOG.md has the
   v2.12.0 section and the missing v2.11.3 section. The shared About changelog lists the
   v2.12.0 public changes against v2.11.3 (Aurral companion, CarPlay beta, Apple TV beta
   from source, Android Auto, the MPRIS artwork, Mixes for you, two Naviamp Connect, Linux
   keyring and two settings-import fixes, Aurral 3 requirement). Every listed fix is merged
   to `main` and ported to `release/2.12.0`. The #637 zip fix is omitted because the defect
   never shipped. On 2026-11-22 `NaviampChangelogTest` (1), `NaviampChangelogRenderedUiTest`
   (2, which scrolls to and displays every About entry) and `NaviampAboutUiTest` (2) passed.
   No milestone issue, PR or comment comes from a community contributor, so there is no
   Thanks section. GitHub notes: `.github/releases/v2.12.0.md`; plain-list Discussion and
   Discord copy: `.github/releases/v2.12.0-announcement.md`.
3. **Linux release zip loses executable permissions — fixed in #638 (issue #637), ported in
   #649.** Verified in WSL: the fixed zip stores all 6 executables as `0755` and
   launches; without the fix the new archive check fails the build. macOS zip not run
   locally (same task and check). Original finding: `bin/Naviamp`, `jspawnhelper` and
   the bundled `.so` files are not executable after unzipping, so the zip does not launch.
   Gradle 9.9.1 (from #610) normalizes archive permissions and `Zip.packageDesktopApp` in
   `apps/desktop/build.gradle.kts` sets none. `.deb`, `.rpm` and the app image are
   unaffected. The macOS zip must be checked for the same defect.
4. **Settings import breaks the active connection — fixed in #640 (issue #639), ported in
   #654.** Connect → Import → enter password → Connect failed with "A connection
   with this provider… already exists" and left no active source, because the imported
   profile was opened as a new connection. It now reconnects the imported profile.
5. **Settings import reset volume to 100 — fixed in #640.** Export intentionally omits
   device-local playback settings; import now keeps the receiving device's volume, output
   device, debug logging and mobile-download values. Owner follow-up (2026-11-21, after a
   Windows retest of the release build without #640): an import that matches a saved
   connection holding credentials reconnects it without a password prompt; a match without
   credentials opens the password form bound to that connection. Verified on Windows with a
   local build of #640 and an isolated profile: export, then import while connected, kept
   the live volume (export carries 100), showed "Settings imported." with no password form
   or duplicate error, left one current connection, and playback continued. The fresh-device
   password path is covered by common tests only.
6. **"Mixes for you" plays the seed album — fixed in #645 (issue #642), ported in
   #650.** Owner decision (2026-11-21): blocks the release; a mix is a pre-filled radio
   station from the seed and never plays the album. Tiles now start seed-track radio filled
   from similar songs; a saved mix replays as track radio; on a remote target the controller
   sends seed-track radio. Verified on Pixel 6a (one-song seed album: seed + 10 similar
   tracks from other artists), onn 4K Pro (Danheim mix: other artists and albums), and
   phone → TV (Redman mix arrives as seed-track radio, never the album).
7. **Choosing one track over Naviamp Control sends only that track — fixed in #646
   (issue #643), ported in #652.** Owner decision (2026-11-21): blocks the release.
   Album and playlist selections now carry their list (optional protocol field; older peers
   keep single-track behavior). Verified phone → TV: tracks 2, 3 and 5 of an 11-track album
   each queued all 11 from the chosen track. One earlier run queued a single track and did
   not reproduce. Search, library, artist and Home track lists still send one track
   (follow-up).
8. **Desktop controller progress stuck at 0:00 — fixed in #647 (issue #644), ported in
   #653.** Owner decision (2026-11-21): blocks the release. Root cause was shared: the
   shell discarded progress while a remote target was attached and targets never sent
   positions. Controllers now extrapolate the target's report from receipt; targets resample
   on resync and publish on seeks. Device testing found the extrapolation anchored at screen
   subscription (23 s behind); fixed and covered by a regression test. Verified phone → TV
   within 1–2 s while playing, after opening Now Playing late, after a seek, and while
   paused. Windows desktop (development profile) → TV: attach mid-track showed the paused
   position (4:16 vs 4:15.7); opening Now Playing late, playback, pause and a scrubber seek
   all stayed within about 1.5 s of the TV.
9. **Linux MPRIS `artUrl` exposed Subsonic credentials — fixed in #656 (issue #655), ported
   in #660.** Native media integrations no longer receive provider URLs. Shared code fetches
   the current artwork through the provider-aware artwork cache, and the desktop writes it
   to a private temporary file published as `file://`; synthetic, failed or remote results
   publish no art. Verified by common tests and desktop MPRIS and artwork-file tests. Not
   verified on a real GNOME/KDE session.
10. **Linux first launch hangs on the keyring — fixed in #658 (issue #657), ported in
    #659.** The Connect device identity loads off the UI thread, and pairing and reconnect
    wait for it. An unavailable secure store is a retryable Connect recovery problem (new
    translated string), and `secret-tool` calls time out after 120 s. Verified by common
    Connect controller tests and the full shared presentation and UI suites. Not verified on
    a real Linux keyring. Follow-up outside this release: revealing the saved source's
    credentials at startup can still wait on a locked keyring on later launches.

Desktop checks for blockers 6 and 7 (Windows, development profile on the same test account
as the TV): a Mixes for you tile played locally queued similar songs from other artists and
saved a seed-track station; the same tile while controlling the TV arrived as seed-track
radio; choosing track 4 of an 11-track album queued all 11 on the TV from that track. Not
covered: replaying a saved mix from Recent Radio in the app (common tests only).

Build note: Windows desktop builds fail in `.claude/worktrees/...` checkouts because MSBuild
hits the path-length limit in the BASS JNI CMake try-compile; building through a short
`subst` drive works.

## Hands-on acceptance: Android TV (onn 4K Pro) and Naviamp Control

Build: `assembleBenchmark` v2.12.0 / 65 on the TV and the Pixel 6a. Control was exercised
between the phone, Windows desktop, TV and the WSL Linux app.

Pass: TV setup by remote, About version, artwork shapes, Library, Search, Internet Radio with
stream titles, playback controls, synced lyrics, auto-advance, background playback, resume and
restore after force-stop. TV CPU (% of one core): Now Playing 6, Home 4.4, paused 1.3,
background 4.2. Control: phone ↔ TV pairing, transport, repeat sync, detach and trusted
reconnect; desktop → TV album playback, transport and seek; phone → desktop queue handoff;
Windows ↔ Linux commands, queue and reconnect.

High:
- "Mixes for you" tiles are titled "<Artist> Mix" but play the seed album
  (`MediaUiMappers.kt` maps them to PlayAlbum), so a one-song album gives a one-track mix.
  Owner expects real multi-track mixes; the server returns 50 similar songs per seed.
- Over Control, choosing one track in an album list sends only that track, and the target
  stops when it ends. Locally the same action queues the album from that track.
- The desktop as controller shows progress stuck at 0:00 while the target plays (the phone
  controller updates live).

Medium: Windows discovery takes 20–35 s and its discovered entries may not verify from the
phone (likely advertising a Tailscale or vEthernet address; manual address works); the
Windows pairing listener can close while the UI still shows a code; the default "Naviamp
Desktop" name cannot be told apart between devices; no seeking with the TV remote; TV text
fields trap D-pad focus and open the keyboard on focus; TV setup shows a raw
`CertPathValidatorException` for a self-signed server.

Not covered: physical remote, TalkBack, setup through Control, the TV as a controller, Cast.

Follow the v2.11.0 [distribution handoff](v2.11.0-readiness.md). Record it in a v2.12.0
handoff with a matching store-copy document, comparing against v2.11.3. Every submission
needs the owner's explicit approval. Upload success, review submission or certification
does not establish availability; verify each channel's live version afterwards.

- **Google Play Alpha:** upload the signed AAB, R8 mapping and native symbols from the tag
  run's `android-publishing-support` artifact to the existing Alpha closed-test track as
  build 65 (v2.12.0). Confirm the signing certificate matches the publishing identity.
  Leave tester enrollment, countries and production access unchanged. Android TV is no
  longer beta, so check whether any Play listing or TV-track copy still says beta.
- **Microsoft Store:** build the unsigned `Naviamp-2.12.65.0.msix` for Store signing with
  the existing identity and Store ID, then create a new submission with updated notes.
- **iOS TestFlight and App Store:** this is the first build with CarPlay. Its entitlements
  request `com.apple.developer.carplay-audio`. Apple must grant that entitlement to the
  App ID and its profiles before a signed archive exports; confirm this before archiving.
  Keep tester notifications off and reuse the existing groups.
- **Mac App Store and macOS TestFlight:** export the 2.12.0 (65) pkg and submit it with
  the same review settings as v2.11.0.
- **Apple TV:** none. It is build-from-source only, so publish no tvOS build.
- **Flatpak:** stage the signed update for v2.12.0 through the existing signing
  environment (v2.11.3-flatpak.1 is live). Do not rotate the key.
- **Community:** prepare the Discord copy from `.github/releases/v2.12.0-announcement.md`
